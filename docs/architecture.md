# Архитектура фронтенда SyncScribe (SyncFront)

Состояние описания: `main @ 4777da0`, 15.10.2026. Бэкенд: [DITLEKS/SyncBack](https://github.com/DITLEKS/SyncBack).
Контракт API берётся из `src/api/openapi.d.ts` (генерируется из `openapi.json` бэкенда); правила экспорта правок сверены с кодом
`app/infrastructure/exporters/*` в SyncBack.

Документ отвечает на два вопроса: что в бэкенде определяет форму фронтенда и как фронтенд устроен, чтобы оставаться чистым при росте.

---

## 1. Что в бэкенде важно для фронтенда

### 1.1. Бэкенд уже спроектирован по DDD — фронт повторяет его словарь

| Слой SyncBack                                           | Что там                                                                                                                      | Что это значит для фронта                                                                                                                                                                                                            |
| ------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `domain/lifecycle.py`                                   | `DocumentLifecycle`: единственное место переходов и разрешённых действий (`can_review`, `can_export`, `can_edit_sources`, …) | Фронт держит такое же единственное место — `src/domain/document/status.ts` (`statusMeta`, `documentPolicy`). В редакторе приоритет у `permissions` из `GET /editor`; `documentPolicy` нужен в списках, где `permissions` нет         |
| `domain/value_objects.py`                               | `DocumentStatusVO` (4 статуса), `AnalysisJobStatusVO` (7), `SourceScopeVO`, `DocumentFormatVO`                               | Словарь домена фронта (`DocumentStatus`) объявлен независимо, а совпадение с OpenAPI проверяется на уровне типов (`src/api/types.ts`, `documentStatusContractMatches`). Дрейф контракта ломает `typecheck`, а не UI в рантайме       |
| `api/schemas/*`                                         | Pydantic-схемы ответов                                                                                                       | Генерируются в `src/api/openapi.d.ts`; руками типы не пишутся. Там, где OpenAPI слабее контракта (`format`, `role`, `view_mode`, `RecentDocumentItem.status` — просто `string`), сужение делает слой `api/types.ts`, а не компоненты |
| `infrastructure/events/sse_broker.py`, `routers/sse.py` | Одно событие `document_status_changed` + `ping` каждые 25 с, только для владельца проекта, требует Bearer                    | Нативный `EventSource` не подходит (нет заголовков): fetch + ReadableStream + собственный парсер (`src/lib/sseParser.ts`, покрыт тестами). Событие несёт только статус — остальное перезапрашивается                                 |
| `infrastructure/exporters/*`                            | Применение принятых правок при экспорте                                                                                      | Определяет алгоритм клиентского «Чистовика» (см. §1.3)                                                                                                                                                                               |
| `main.py`                                               | CORS без `*`, `expose_headers: Content-Disposition, Retry-After`; `DomainError → 400`, валидация → 422 с массивом `detail`   | `getErrorMessage` разбирает оба формата `detail`, 429 дополняет `Retry-After`; имя файла экспорта читается из `Content-Disposition` (`filename*`, затем `filename`)                                                                  |

### 1.2. Факты контракта, которые определяют архитектуру

- **Статусы.** Документ — ровно 4 публичных статуса; техническое состояние анализа — отдельное поле `analysis`
  (`state`, `error_code`, `error_message`, `can_retry`). Ошибка анализа не статус, а причина у `draft`.
- **Сервер не меняет текст при принятии правок.** `content.plain_text` и `original_content.plain_text` в `GET /editor` —
  один и тот же исходный текст. Режимы «Правки» и «Чистовик» — чисто клиентская проекция (`domain/editor/projection.ts`).
- **Ревью — оптимистическая блокировка.** `PUT /suggestions/review` с `If-Match: <review_version>`; `412` — версия устарела,
  `409` с `finalize=true` при остатке `pending`. Клиент обязан сам вычислять `finalize` и не допускать 409.
- **Одна активная задача на документ, идемпотентный запуск.** `Idempotency-Key` (UUID v4 на клик); из `ready` — только `force=true`
  после подтверждения (`409 { confirmation_required: true }`).
- **Источники заморожены** только в `in_progress` (`423`).
- **Чужой ресурс — 404**, не 403. UI не различает «нет» и «не моё».
- **Токены.** Refresh ротируется, повторное использование старого — `401`. Отсюда single-flight refresh с общей очередью.

### 1.3. Как сервер применяет правки при экспорте (определяет «Чистовик»)

Правила экспортёров `TextExporter` и `DocxExporter` в SyncBack:

| Тип      | txt / markdown                                                                  | docx                                                                                       |
| -------- | ------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| `modify` | `text.replace(old, new, 1)` — первое вхождение во всём тексте, не внутри секции | первый абзац, содержащий `old`; внутри абзаца — первое вхождение                           |
| `delete` | то же, с пустой заменой                                                         | то же, с пустой заменой                                                                    |
| `add`    | новый абзац сразу после строки, содержащей якорь (`original_text`)              | новый абзац сразу после абзаца с якорем; без якоря или с ненайденным якорем не вставляется |

Для `modify` и `add` новый текст — `edited_text` (если пользователь правил текст при принятии), иначе `suggested_text`.

Таблица выше — для правок без границ. Правка с границами (`start_offset`/`end_offset`, под которыми в `plain_text` лежит
её `original_text`) применяется на своём месте, а не в первом вхождении: все такие правки сначала применяются одним проходом
к исходному тексту (`text_edits.apply_edits`), устойчиво отсортированные по началу (для `add` — по концу строки якоря);
правка с началом внутри уже применённой пропускается. В docx — то же внутри абзаца, добавления встают за абзацем в порядке выдачи.
Остальные правки затем применяются последовательно в порядке `(created_at, position, id)`, каждая — к уже изменённому тексту.

Следствия для клиента:

1. Правка с границами показывается на своём месте; пропущенная из-за пересечения получает `overlap` и не экспортируется.
   Смещения сервера — в кодовых точках, перевод в UTF-16 — `domain/editor/offsets.ts`, один раз на текст.
   Для правки без границ поиск `original_text` — первое вхождение во всём `plain_text`, как на сервере. `section_ref` нужен для навигации и для предупреждения
   «фрагмент найден вне указанной секции», но не для выбора вхождения. Иначе «Чистовик» и экспорт разойдутся.
2. `add` в «Чистовике» встаёт после строки с якорем. Если якоря нет или он не найден, сервер добавление не применит, и клиент место за него не выбирает:
   правка получает пометку `not_found` и не считается экспортируемой.
3. В docx фрагмент ищется внутри одного абзаца, поэтому правка с переводом строки не применится (`not_applicable`).
4. Пересекающиеся правки: если фрагмент задевает текст другой правки, UI не показывает её внутри текста и предупреждает,
   что результат экспорта может отличаться (`overlap`).

## 2. Принципы

1. **Домен не знает о React и HTTP.** `src/domain/**` — чистый TypeScript: статусная модель, политика действий, применение правок,
   буфер решений ревью. Это самый тестируемый и самый рискованный код; он покрывается unit-тестами без DOM.
2. **Один источник правды на каждое знание.** Лейблы и цвета статусов — `statusMeta`; ключи кеша — `queryKeys`; разбор ошибок —
   `getErrorMessage`; лимиты загрузки — `useCapabilities()`; пути — `routes`.
3. **Сгенерированный контракт — граница.** `openapi.d.ts` не редактируется; всё, что контракт выражает слабо, уточняется в `api/types.ts`.
   Это антикоррупционный слой между транспортом и доменом фронта.
4. **Серверное состояние ≠ локальное состояние.** Серверное — только в TanStack Query (кеш, инвалидация, SSE-патчи).
   Локальное — Zustand только там, где есть настоящая клиентская модель: буфер решений редактора, выбранная правка, режим просмотра.
   Никакого дублирования серверных данных в сторах.
5. **Фича — bounded context с публичным API.** Снаружи фичи доступен только `index.ts`. Это проверяет ESLint (`eslint-plugin-boundaries`),
   а не договорённость.
6. **Честные состояния.** Каждый экран имеет загрузку (скелетоны), пустое состояние (тексты из UI-описания дословно) и ошибку
   (сообщение сервера + «Повторить»). Нет «хаков» вроде повторов до успеха.

## 4. Ключевые механизмы

### 4.1. Аутентификация

- `authSession` — модуль без React. Access-токен в памяти, refresh — в `localStorage` (осознанный компромисс: бэкенд не ставит httpOnly cookie).
- Refresh — single-flight: параллельные вызовы получают один промис; новая пара сохраняется атомарно до резолва ожидающих.
  Любая ошибка refresh очищает сессию и уведомляет подписчиков (`AuthProvider` → `/login?returnTo=`).
- Проактивное обновление за 60 с до `expires_in` (таймер) и реактивное на 401 (middleware клиента, ровно один повтор на запрос;
  копия запроса делается в `onRequest`, потому что тело оригинала уже прочитано).
- `AuthProvider` восстанавливает сессию при старте одним refresh, затем `GET /auth/me` через TanStack Query. Регистрация не выдаёт токены — сразу вызывается login.
- Rate limit (429) показывается с `Retry-After`, запрос не повторяется.

### 4.2. Серверное состояние и инвалидация

- Ключи — `queryKeys` с иерархией (`['documents', 'project', id, params]`), чтобы инвалидировать срезами.
- Мутации инвалидируют по ключам; оптимистические обновления только в буфере решений редактора (это локальное состояние, а не кеш сервера).
- Исходный файл документа для режима «Оригинал» загружается один раз (`staleTime: Infinity`) и только когда режим открыт.
- Файлы источников и документов скачиваются через авторизованный API как `Blob` (`lib/downloadBlob.ts`), браузер не обращается к хранилищу напрямую.
- SSE-событие `document_status_changed` → `setQueryData` для детали документа (статус и `current_analysis_job_id`) и инвалидация списков,
  дашборда, attention/recent; для открытого редактора — повторный `GET /editor` с сохранением буфера.

### 4.3. Реальное время

`RealtimeProvider` внутри защищённого layout держит одно соединение: `fetch` + `ReadableStream` + `createSseParser`, `AbortController`.
Переподключение 1 → 30 с с удвоением, сброс после открытия; на 401 — сначала `authSession.refresh()`, при неудаче соединение останавливается.
Watchdog: 60 с без данных (сервер пингует раз в 25 с) → переподключиться; тот же таймаут страхует повисший запрос.
После переподключения кеш документов, проектов и дашборда перечитывается.
Fallback: состояние соединения в Zustand (`useRealtimeStore`); пока его нет, списки и деталь документа с `in_progress` опрашиваются раз в 5 с,
дашборд — раз в 15 с. С соединением опроса нет.

### 4.4. Редактор

Доменная модель в `src/domain/editor/` (без React):

- `buildProjection({ text, sections, format, suggestions, statusOf, newTextOf })` — сегменты `text | change` по правилам сервера (§1.3)
  и для каждой правки `issue` (`not_found`, `overlap`, `not_applicable`, `outside_section`) и признак `exportable`.
  Статус берётся из `statusOf`: серверный статус поверх буфера. Новый текст берётся из `newTextOf`: текст пользователя важнее текста ИИ.
- `exportedText(projection, format)` — итоговый текст экспорта; тесты сверяют его с поведением серверных экспортёров.
- `planSave(serverSuggestions, buffer, serverPendingCount)` → `{ decisions, finalize, stale }`: в `decisions` только серверные `pending`
  (с `edited_text`, если он есть), `finalize = true` только если после сохранения `pending` станет 0.
- `reviewProgress(counters, suggestions, buffer)` — счётчики и процент с учётом несохранённых решений.

Режимы просмотра: «Оригинал», «Правки», «Чистовик» (`ViewMode`).

- **txt и markdown.** `DocumentText` рисует сегменты проекции по абзацам; сегменты мемоизированы по содержимому,
  поэтому решение по одной правке перерисовывает только её фрагмент.
- **docx.** Оригинал рисует `docx-preview` (`OriginalDocxView`, `renderDocx`). В режимах «Правки» и «Чистовик» (`DocxSuggestionsView`)
  правки привязываются к DOM готового документа: правка с границами — к абзацу своего блока (номер среди непустых абзацев,
  сверка по тексту блока), остальные `anchorSuggestions` ищет по `original_text` в абзацах так же, как сервер
  (первое вхождение внутри одного абзаца), и оборачивает фрагмент в `<span data-suggestion-id>`; `decorateAnchor` показывает его
  как правку или как чистовой текст. Форматирование внутри фрагмента сохраняется. Для добавлений место в docx-представлении
  выбирается по концу раздела `section_ref` (последний уникальный абзац раздела): это визуальное приближение, на экспорт оно не влияет.

Панель «Предложения ИИ» (`SuggestionsPanel`) сворачивается, остаётся под шапкой, прокручивается только при переполнении.
Список длиннее 100 правок (`VIRTUALIZE_FROM`) виртуализируется через TanStack Virtual; короткий рисуется целиком.
Выбор правки из текста прокручивает список к её карточке. Карточка (`SuggestionDetails`) позволяет изменить предложенный текст перед принятием.

Флаги «проверьте вручную» (`AnalysisFlag`) — места, где ИИ не предложил правку, но просит сверить текст с источниками.
Они приходят в `GET /editor` (`flags`, `counters.flags_pending`) и показываются разделом над списком правок (`FlagsSection`);
в тексте блок флага (`block_id` → `content.blocks[].ref`) отмечен пунктирной рамкой слева (`data-flag-id`), в docx — абзац
(`anchorFlags`, тот же поиск абзаца, что у правок с границами). В «Чистовике» флаги не размечаются. Отметка «Просмотрено» /
«Вернуть» — `PATCH …/flags/{id}` сразу, мимо буфера ревью (на сохранение решений, finalize и экспорт флаг не влияет): кеш
меняется оптимистично, при ошибке откатывается; `404` (флаг прежнего анализа) и `409` (документ не в ревью) перечитывают редактор.

Решения и правки текста хранятся в буфере (Zustand, `features/editor/model/reviewBuffer.ts`), привязанном к `document_id + current_analysis_job_id`.
Буфер не входит в кеш запросов, поэтому перезапрос редактора (SSE, конфликт версий) его не стирает.

Сохранение: `PUT …/suggestions/review` с `If-Match`; `412` и `409` → баннер «Документ изменён в другой сессии», перезапрос `GET /editor`,
буфер сохраняется. Ответ сохранения применяется к кешу до перезапроса, включая `edited_text`. Уход со страницы с непустым буфером —
`useBlocker` + `beforeunload` (`LeaveGuard`). Отмена уже сохранённого решения — `PATCH {ids, status: "pending"}` сразу, без буфера
(работает и в `ready`, документ возвращается в `awaiting_approval`). Сброс решений и сброс ревью — отдельные запросы с подтверждением.
Экспорт — `GET …/export` как `Blob`, имя файла из `Content-Disposition`. Для доступности статус сохранения, конфликт и число
несохранённых решений дублируются в скрытой `aria-live` области.

### 4.5. Загрузка документа и источники

Диалог загрузки из двух шагов: файл, затем источники документа и кнопка «Сохранить». Документ создаётся черновиком (`draft`),
анализ запускается отдельным действием: из строки документа или из его страницы (`POST …/analysis-jobs` с `Idempotency-Key`).
Последовательность в `features/documents/model/uploadFlow.ts`: `POST /projects/{p}/documents` → источники `scope=document`
(→ при необходимости анализ). Транзакции нет: если источник не добавился, анализ не запускается, документ остаётся в `draft`,
повтор отправляет только оставшиеся источники и не загружает файл заново. Расширение и размер проверяются на клиенте по capabilities;
413/415/422 сервера показываются как есть.

Базовые источники проекта показываются на странице проекта отдельным блоком; в строке документа — только его собственные.
У источника можно посмотреть содержимое, скачать файл и увидеть дату добавления. Пока документ в `in_progress`,
сервер отвечает 423, и клиент блокирует изменение источников (`lockedReason`).

## 7. Известные ограничения

1. **Место добавления в docx-представлении.** Экспорт ставит добавление после абзаца с якорем, а представление docx показывает его в конце раздела `section_ref`.
   Если место важно визуально, нужен якорь по `original_text` и в docx-представлении.
2. **Источник правки.** В контракте нет поля со ссылкой на источник, поэтому карточка правки его не показывает.
3. **Поиск по всему тексту.** Для правок без границ (прежний конвейер или рассинхрон с текстом) сервер заменяет первое вхождение,
   и клиент повторяет это. Нумерация абзацев `docx-preview` и `DocxParser` совпадает по предположению; при расхождении абзац
   ищется по тексту блока, а затем — общим поиском.
4. **Повторный анализ из `awaiting_approval`.** Сервер запускает его без подтверждения и сбрасывает решения; клиентский диалог
   подтверждения (`force=true`) показывается только из `ready`, из `awaiting_approval` анализ стартует сразу.
5. **Источники документа.** Они берутся из `include=documents` с лимитом 200; отдельного фильтра по документу в `GET …/sources` нет.
6. **Пароль.** Политика сложности видна только по тексту 422; описания политики в `/system/capabilities` нет.
