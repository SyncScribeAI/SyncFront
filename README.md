# SyncFront

Веб-клиент **SyncScribe** — сервиса, который сверяет документы с источниками, предлагает правки и помогает их рассмотреть.
Работает только с бэкендом [SyncBack](https://github.com/SyncScribeAI/SyncBack) (FastAPI). Анализ документов выполняет ML-конвейер [syncscribe-ml](https://github.com/rishotkaB/syncscribe-ml), который бэкенд вызывает по контракту 2.0; с ML-сервисом фронтенд напрямую не взаимодействует.

## Возможности

- Регистрация и вход, автоматическое обновление сессии.
- Проекты: создание, переименование, удаление. Цвет и иконка проекта приходят с сервера.
- Источники: базовые источники проекта (для всех его документов) и источники отдельного документа. Просмотр, скачивание, добавление; во время анализа изменение источников заблокировано сервером.
- Документы: загрузка в два шага с проверкой формата и размера, групповой запуск анализа, удаление с подтверждением.
- Анализ: запуск, отмена, ход выполнения и ошибки в реальном времени.
- Дашборд: метрики, динамика, недавние документы, документы, которым нужно внимание, быстрые действия.
- «Мои документы»: поиск и фильтр по статусу (хранятся в URL), доля рассмотренных правок по каждому документу.
- Редактор правок (подробнее ниже).

Все экраны показывают скелетон при загрузке, текст пустого состояния и ошибку сервера с кнопкой «Повторить».

## Редактор правок

- Режимы «Оригинал», «Правки» и «Чистовик». Для `.docx` оригинал и правки отображаются через docx-preview, для текста используется собственный рендер по абзацам, markdown форматируется через react-markdown с подсветкой правок и флагов в разметке.
- Панель «Предложения ИИ» сворачивается, прокручивается при переполнении; списки длиннее 100 правок виртуализируются.
- Решения (принять, отклонить) накапливаются локально и сохраняются одним запросом с проверкой версии (`If-Match`). Отмена уже сохранённого решения отправляется сразу. Если ревью изменили в другом месте, несохранённые решения не теряются.
- Диалог при уходе со страницы с несохранёнными решениями, сброс ревью.
- Экспорт файла доступен, когда сервер разрешил его для документа.
- Текст, отредактированный пользователем при принятии правки, учитывается в «Чистовике» и в экспорте.
- Чистовик строится на клиенте по тем же правилам, что и экспорт на сервере: правка с границами (`start_offset`/`end_offset`) применяется на своём месте, остальные — к первому вхождению исходного текста, добавление встаёт после строки с якорем. Если якорь не найден, сервер добавление не применит, и клиент его место не выбирает.

### Возможности контракта 2.0

Эти данные бэкенд заполняет при анализе по контракту 2.0 (`ANALYSIS_PROVIDER` = `ml_http`, `ml_plugin` или `stub`). При прежнем конвейере (`legacy_llm`) их нет, и редактор работает по тексту, как описано выше.

- **Блоки и границы.** Документ приходит списком блоков (`content.blocks`: `ref`, тип, границы, `editable`). Правка с `block_id` и границами подсвечивается в своём блоке, в том числе в `.docx`: абзац docx-preview находится по номеру блока, а при расхождении — по тексту.
- **Порядок.** Правки и флаги идут в порядке документа (`position`), а не в порядке ответа модели.
- **Низкая уверенность.** Правка с `confidence_score` ниже 0.7 получает отметку «Проверьте внимательно». Порог совпадает со значением по умолчанию `SUGGESTION_LOW_CONFIDENCE_THRESHOLD` в SyncBack.
- **Частичный анализ.** Если конвейер проверил не все блоки или часть источников была недоступна (`partial_success`), над текстом показывается предупреждение с причиной. Правки при этом можно рассматривать как обычно.
- **«Проверьте вручную».** Флаги — места, где ИИ не предложил правку, но просит сверить фрагмент с источниками, например когда источники противоречат друг другу (`sources_conflict`). Флаг показывается в тексте и в отдельном разделе панели с цитатами источников; его можно отметить как просмотренный. Флаги не влияют на статус документа и экспорт. Неизвестный код причины показывается как «Проверьте вручную».
- **Основания правок.** Источник в карточке правки открывается в том виде, в каком его читал анализ, с подсвеченной цитатой. Если оснований несколько, их можно листать. Оригинал `.docx` показывается с подсветкой абзаца, оригинал `.pdf` с подсветкой строк цитаты, остальные форматы текстом снимка с таблицами; ненайденная цитата показывается отдельно.
- **Группы.** Правки одной фразы в разных местах документа (`group_key`) объединяются: «Принять все», «Отклонить все», переход к следующему вхождению. Правки, найденные сервером по образцу, помечены «Найдено автоматически». Решение по группе потом можно изменить для каждой правки отдельно.

## Стек

React 18 + TypeScript (strict), Vite 5, React Router v6, TanStack Query v5, TanStack Virtual, Zustand, Tailwind CSS 3.4 + shadcn/ui (Radix), sonner, lucide-react, react-hook-form + zod, docx-preview, openapi-typescript + openapi-fetch, Vitest + React Testing Library + MSW, ESLint (typescript-eslint strict, eslint-plugin-boundaries) + Prettier.

## Запуск

Нужны Node 20 (версия указана в `.nvmrc`) и запущенный бэкенд: `docker compose up --build` в репозитории SyncBack, API на `http://localhost:8000`.

```bash
cp .env.example .env
npm install
npm run dev          # http://localhost:5173, запросы к /api проксируются на бэкенд
```

Пользователь создаётся через экран регистрации. Для разработки интерфейса ML-конвейер не нужен:

- `ANALYSIS_PROVIDER=stub` в `.env` бэкенда — анализ по контракту 2.0 без внешних вызовов, с тестовыми правками;
- `ANALYSIS_PROVIDER=legacy_llm` и `LLM_PROVIDER=stub` — прежний конвейер без блоков, флагов и групп.

Для анализа реальной моделью бэкенд запускают с `ANALYSIS_PROVIDER=ml_http` и `ML_ENDPOINT`, указывающим на `POST /v1/analyze` сервиса syncscribe-ml (см. README бэкенда и ML-конвейера).

## Скрипты

| Команда                           | Что делает                                                                               |
| --------------------------------- | ---------------------------------------------------------------------------------------- |
| `npm run dev`                     | dev-сервер Vite с прокси `/api` на `VITE_DEV_PROXY_TARGET`                               |
| `npm run build`                   | проверка типов и сборка в `dist/`                                                        |
| `npm run preview`                 | локальный просмотр собранного приложения                                                 |
| `npm run typecheck`               | проверка типов без сборки                                                                |
| `npm run lint`                    | ESLint; предупреждения считаются ошибками                                                |
| `npm run test` / `test:watch`     | тесты Vitest (jsdom, MSW)                                                                |
| `npm run format` / `format:check` | Prettier                                                                                 |
| `npm run api:types`               | перегенерировать `src/api/openapi.d.ts` из `OPENAPI_URL` (по умолчанию `localhost:8000`) |

Файл `src/api/openapi.d.ts` лежит в репозитории, чтобы проверка типов работала без запущенного бэкенда. После изменения API на бэкенде его нужно перегенерировать и закоммитить.

Бэкенд хранит актуальную схему в `docs/openapi.json`, поэтому типы можно сверить и без запуска бэкенда, если SyncBack лежит рядом:

```bash
OPENAPI_URL=../SyncBack/docs/openapi.json npm run api:types
git diff --stat src/api/openapi.d.ts   # пусто — типы фронтенда совпадают со схемой бэкенда
```

## Переменные окружения

| Переменная              | Назначение                                                                                                                                                    |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `VITE_API_BASE_URL`     | Базовый URL API для production-сборки. В dev пустой: работает прокси. При прямых запросах к API origin фронтенда должен быть в `CORS_ALLOWED_ORIGINS` бэкенда |
| `VITE_DEV_PROXY_TARGET` | Куда Vite проксирует `/api` в dev (по умолчанию `http://localhost:8000`)                                                                                      |
| `OPENAPI_URL`           | Откуда брать OpenAPI для `npm run api:types`                                                                                                                  |

## Структура

```
src/
  app/            провайдеры, роутер, layout, ErrorBoundary
  pages/          тонкие страницы
  features/       модули по предметным областям: auth, projects, sources, documents,
                  analysis, dashboard, editor, sse, system; снаружи доступен только index.ts
  domain/         чистый TypeScript без React: статусы, правила анализа, проекция правок, правила ревью
  api/            сгенерированные типы, клиент с auth-middleware, функции по ресурсам, ключи запросов
  components/ui/  примитивы shadcn/ui
  lib/            утилиты: ошибки, форматирование, SSE-парсер, хранилище, скачивание файлов, хуки, просмотр docx, Markdown и PDF
  test/           настройка тестов, MSW-хендлеры, тесты экранов
```

Зависимости между слоями проверяет ESLint (`eslint-plugin-boundaries`): `domain` не знает о React и API, фичи общаются друг с другом только через публичный `index.ts`.

## Как это работает

- **Авторизация.** Access-токен хранится в памяти, refresh-токен в `localStorage`. Обновление пары выполняется в одном экземпляре с очередью ожидающих запросов: за 60 секунд до истечения и повторно при ответе 401. Неудачное обновление очищает сессию и ведёт на `/login?returnTo=…`.
- **Серверное состояние.** Данные API кешируются в TanStack Query; решения редактора хранятся отдельно в Zustand, чтобы перезапрос данных не стирал несохранённые правки.
- **Реальное время.** Один SSE-канал на пользователя: события документа обновляют кеш, при обрыве клиент переподключается с нарастающей задержкой. Статусы, ход анализа и дашборд работают от этих событий без опроса.
- **Лимиты и форматы загрузки** берутся из `GET /system/capabilities`, в коде они не зашиты.
- **Файлы** источников и документов скачиваются через API.
- **Экспорт** выполняется в исходном формате документа.
- **Доступность.** Области нажатия иконок 44 px, `aria-live` для статуса сохранения в редакторе, учёт `prefers-reduced-motion`.

## Известные ограничения

Полный список — в разделе 7 [`docs/architecture.md`](docs/architecture.md). Главное:

- В `.docx` без блоков (прежний конвейер) добавление показывается в конце раздела, хотя экспорт ставит его после абзаца с якорем. С контрактом 2.0 оно стоит после своего абзаца.
- В контракте нет ссылки правки на конкретный источник: сервер приписывает правке все источники анализа, и карточка показывает их все.
- Порог низкой уверенности 0.7 задан в коде и повторяет значение бэкенда по умолчанию; если на бэкенде порог изменят, его нужно поменять и здесь.

## Развёртывание

Сборка (`dist/`) статическая. Кроме кода в ней лежит каталог `dist/pdfjs/` с ресурсами pdf.js (cmaps, стандартные шрифты, wasm, ICC-профили): просмотр PDF берёт их со своего origin, без CDN. Веб-сервер должен отдавать `.mjs` с типом `text/javascript` (воркер pdf.js) и `.wasm` с типом `application/wasm`.

## Проверки и CI

Перед коммитом:

```bash
npm run format:check && npm run typecheck && npm run lint && npm run test && npm run build
```

CI (`.github/workflows/ci.yml`) выполняет эти шаги на Node 20, а проверку типов, линтер и тесты дополнительно запускает на Node 22 и 24.
